### 1. K-means 군집화 최종 비교 실험

#### 1-1. 실험 목적

수학 문제를 BoW 빈도 벡터로 표현했을 때, K-means가 실제 교육과정상의 분류와 어느 정도 일치하는지 확인합니다.

특히 기존에 사용한 유클리드 거리 기반 K-means와 **코사인 유사도 기반 군집화**를 비교하여, 문제의 길이와 전체 토큰 등장 횟수가 군집 형성에 영향을 주었는지 검토하고 싶습니다.

#### 1-2. 비교할 실제 분류 단계

다음 네 단계를 각각 독립적으로 실험합니다.

1. 과목
2. 단원
3. 세부단원
4. 문제 유형

현재 데이터의 메타데이터에는 `subject`, `curriculum`, `unit`, `subunit`, `type` 필드가 있는 것으로 파악됩니다.

이 필드들의 실제 값과 의미를 확인하여, 위 네 단계에 대응되는 올바른 라벨을 사용해 주세요.

특히 `subject`는 미분·삼각함수라는 자료군을 구분하는 데 사용되는 것으로 보이므로, 과목을 의미하는 `curriculum`과 혼동하지 마세요.

분류명이 서로 다른 상위 범주에서 중복될 경우, 상위 분류 경로를 포함한 고유 라벨을 만들어야 합니다. 예를 들어 서로 다른 단원에 같은 이름의 유형이 있더라도 같은 유형으로 합쳐지지 않도록 처리해 주세요.

각 단계의 **실제 고유 분류 수를 학습 데이터에서 계산하고**, 해당 분류 수를 K-means의 군집 수 `k`로 사용합니다. 전체·학습·테스트에서 관찰되는 라벨 수는 별도로 표시하여 차이를 확인할 수 있게 해 주세요.

분류 단계별 고유 라벨 목록, 각 라벨의 문항 수, 적용한 군집 수를 저장해 주세요. 기존에 사용한 2·8·70이라는 숫자를 무조건 하드코딩하지 말고 실제 필드와 고유 경로를 확인해 결정합니다.

#### 1-3. 비교할 군집화 방법

동일한 데이터에 다음 두 가지 방법을 적용합니다.

**A. 유클리드 거리 기반 K-means**

- 기존 구현을 최대한 유지합니다.
- 원시 BoW 빈도 벡터를 사용합니다.
- 유클리드 거리를 기준으로 군집을 배정합니다.
- 군집 중심은 해당 군집에 속한 벡터의 산술평균으로 갱신합니다.

**B. 코사인 유사도 기반 K-means**

- 코사인 유사도에 기반한 **Spherical K-means**를 구현하거나 검증된 구현을 사용합니다.
- 입력 벡터를 L2 정규화합니다.
- 코사인 유사도를 기준으로 군집에 배정합니다.
- 중심 갱신 후에도 중심 벡터를 정규화합니다.
- 영벡터, 빈 군집 등의 예외를 안전하게 처리합니다.

단순히 기존 K-means의 거리 계산만 코사인 유사도로 바꾸고 중심 갱신은 그대로 두는 식의 불완전한 구현은 피해주세요.

두 방식의 비교에서 **거리 기준과 이에 필요한 정규화·중심 갱신 이외의 조건은 최대한 동일하게 유지**해 주세요.

학습·테스트 데이터 분할, 입력 어휘, 군집 수, 반복 횟수 및 초기화 재시작 횟수 등을 통제합니다.

초기화에 의한 결과 변동을 줄이기 위해 기존처럼 여러 시드로 실행하고, 각 방식의 학습 목적함수에 따라 최적 실행을 선택해 주세요. 서로 다른 목적함수의 값 자체를 직접 비교하지는 마세요.

이번 비교에 불용어 제거·TF-IDF·새 임베딩을 동시에 추가하지 않습니다. 별도로 요청하지 않은 전처리 개선은 후속 과제로만 남겨 주세요.

#### 1-4. 군집화 성능 평가

각 분류 단계와 군집화 방식에 대해 다음을 계산합니다.

- ARI(Adjusted Rand Index)
- NMI(Normalized Mutual Information)
- 각 군집에서 가장 빈번한 실제 라벨을 기반으로 한 분류 정확도(보조 지표)
- 실제로 형성된 군집 수와 각 군집의 문항 수

군집의 대표 라벨을 정할 때는 **학습 데이터만 사용**하고 테스트 데이터의 실제 라벨을 참고하지 않습니다.

군집화 모델의 중심도 학습 데이터에서만 계산합니다. 테스트 데이터는 학습된 중심을 기준으로 배정하고 평가에만 사용합니다.

실제 유형과 군집 번호의 일치도를 평가할 때는 군집 번호가 임의의 숫자라는 사실을 고려해 주세요.

특히 세부단원이나 유형의 종류가 많은 반면 문항 수가 적을 수 있으므로, 점수의 한계와 해석상 주의점도 명시해 주세요.

#### 1-5. 군집 내부를 직접 관찰할 수 있는 출력

이번 작업에서 특히 중요한 요구사항입니다.

단순히 ARI나 NMI 숫자만 출력하는 것이 아니라, **각 군집에 실제 어떤 문제가 들어갔는지 사람이 직접 확인할 수 있도록** 저장해 주세요.

각 실험에 대해 최소한 다음 정보가 필요합니다.

- 군집 번호
- 해당 군집에 포함된 문항 ID 목록
- 학습·테스트 구분
- 각 문항의 실제 과목·단원·세부단원·유형
- 군집별 실제 라벨의 빈도와 비율
- 군집에서 가장 많은 실제 라벨
- 한 실제 분류가 여러 군집에 분산된 정도

가능하면 원본 문제 텍스트를 쉽게 확인할 수 있도록 문항 ID와 파일 경로도 함께 표시해 주세요.

최종적으로 다음 자료를 만들어 주세요.

1. 전체 실험의 ARI·NMI 비교표
2. 각 군집의 실제 문항과 라벨을 확인할 수 있는 CSV
3. 실제 분류와 군집 번호의 교차표 및 히트맵
4. 대표적인 군집 성공·실패 사례 요약

결과를 직접 관찰하는 것이 목적이므로 출력의 가독성을 우선해 주세요.

### 2. 선형회귀 모델의 해설 빈도 벡터 예측 성능 검증

#### 2-1. 실험 목적

문제의 BoW 빈도 벡터를 입력하여 실제 해설의 BoW 빈도 벡터를 예측하는 선형회귀 모델의 성능을 확인합니다.

단순히 손실함수가 감소했는지 확인하는 것뿐만 아니라, **예측된 해설 벡터가 실제 해설의 주요 특징을 얼마나 잘 표현하는지** 알고 싶습니다.

#### 2-2. 평가 조건

기존 학습·테스트 분할을 유지합니다.

테스트 데이터의 실제 해설 벡터는 학습에 사용하지 않습니다.

다음 세 가지를 비교합니다.

- 학습 데이터의 평균 해설 벡터만 사용하는 기준 모델
- 선형회귀 모델의 원시 출력
- 선형회귀 모델의 음수 예측값을 0으로 보정한 출력

평가 지표는 다음과 같습니다.

- MSE
- MAE
- 코사인 유사도

분류 정확도처럼 단일한 ‘정답률’을 제시하기보다는, 연속적인 벡터 예측의 성능을 위 지표들로 평가해 주세요. 코사인 유사도를 퍼센트 정답률로 해석하지 마세요.

#### 2-3. 실제 해설 벡터와 예측 벡터 비교

테스트 문항별로 다음 정보를 저장해 주세요.

- 문항 ID
- 실제 해설 빈도 벡터
- 예측 해설 빈도 벡터
- 문항별 MSE·MAE·코사인 유사도
- 실제 해설에서 빈도가 높은 토큰 20개
- 예측 해설에서 빈도가 높은 토큰 20개
- 두 상위 20개 토큰 집합의 일치 정도

상위 20개 토큰에 대해서는 공통 토큰 개수 및 Precision@20 등의 지표를 사용해 주세요. 비교 기준과 동률 처리 방법도 명시해 주세요. 양의 빈도를 가진 토큰이 20개 미만일 때의 처리 및 지표 분모도 명확히 기록합니다.

특히 예측 성능이 좋은 문항과 나쁜 문항을 각각 확인할 수 있도록 정렬 가능한 CSV 또는 별도 요약 자료를 만들어 주세요.

#### 2-4. 소수점 및 음수 처리

원본 텍스트에서 직접 계산한 실제 빈도 벡터는 정수라는 점을 유지합니다.

하지만 회귀 모델의 예측값은 실수이므로, **회귀 모델 평가 단계에서는 정수 반올림하지 마세요.**

음수 보정 전후의 평가를 구분하고, LLM에 전달할 때 사용하는 값의 처리 방법도 기록해 주세요.

정수 반올림으로 정보를 잃지 않도록 기존의 소수점 세 자리 표시 방식을 유지해도 좋습니다. 원시 예측값은 별도로 보존하고, 상위 토큰 선택에 사용하는 값과 전송용 표시 값을 구분해 주세요.

### 3. Gemini API를 이용한 최종 비교 실험

#### 3-1. 실험 목적

해설 빈도 벡터를 추가 정보로 제공하는 것이 Gemini의 수학 문제 풀이에 도움이 되는지 검증합니다.

특히 개선이 나타나지 않을 경우 다음 두 가능성을 구분하고 싶습니다.

- 회귀 모델의 해설 빈도 예측이 부정확했기 때문인가?
- 해설의 빈도 벡터라는 정보 자체가 수학 문제 풀이에 충분히 유용하지 않기 때문인가?

이를 위해 세 조건을 비교합니다. 이 비교는 원인을 탐색하는 실험이며, 결과 하나로 원인을 확정하지 마세요.

#### 3-2. 비교 조건

**A. 기본 조건: 문제만 제공**

- 원본 수학 문제만 Gemini에 전달합니다.
- 빈도 벡터나 실제 해설은 제공하지 않습니다.
- 기존 기본 모델의 풀이 성능을 측정합니다.

**B. 예측 벡터 조건: 문제 + 회귀 모델의 예측 해설 벡터**

- 원본 수학 문제를 제공합니다.
- 학습된 선형회귀 모델이 예측한 해설 빈도 벡터를 추가합니다.
- 예측 빈도가 높은 상위 20개 토큰을 기존 방식과 동일하게 제공합니다.

**C. 실제 해설 벡터 조건: 문제 + 정답 해설의 실제 빈도 벡터**

- 원본 수학 문제를 제공합니다.
- 해당 문항의 실제 해설에서 계산한 빈도 벡터를 추가합니다.
- B와 동일한 방식으로 빈도가 높은 상위 20개 토큰을 제공합니다.

C 조건은 회귀 모델을 거치지 않았을 때 해설 빈도 정보가 얼마나 유용한지 알아보는 **오라클(oracle) 실험**입니다.

실제 해설 벡터에는 정답이나 풀이에 직접 연결되는 토큰이 포함될 수 있습니다. 따라서 C 조건을 실제 서비스의 예측 성능처럼 해석하지 말고, 정답 해설 정보를 미리 제공하는 참고 조건이라는 점을 명시해 주세요.

B와 C는 같은 토큰 개수, 정렬 규칙, 반올림 방식 및 프롬프트 구조를 사용하되, 정보의 출처만 다르도록 해주세요. C 조건이라고 실제 해설의 문장 전체나 별도의 정답 표기를 추가하지 않습니다.

실제 해설 벡터도 기존 학습 어휘에 대응하는 벡터를 사용하고, 테스트 해설을 보고 새로운 어휘를 추가하지 마세요. 따라서 C는 전체 해설 정보의 제공이 아니라, 고정 어휘·상위 토큰이라는 동일한 표현 조건 안에서의 진단용 비교입니다. C가 이론적 성능 상한이라고 보장하지도 않습니다.

#### 3-3. 실험 조건 통제

세 조건에 대해 다음을 동일하게 유지합니다.

- 동일한 테스트 문항 80개
- 동일한 Gemini 모델
- 동일한 temperature 및 thinking 설정
- 동일한 최대 출력 토큰 설정
- 동일한 기본 지시문과 출력 형식
- 동일한 정답 평가 기준

기존 실험 설정과 실행 기록을 우선 확인하고, 가능하다면 그대로 재사용해 주세요.

기존 A·B 응답이 동일한 설정과 동일한 입력으로 이미 실행되어 있다면 무조건 재호출하지 말고, 설정·입력 해시 등을 검증한 뒤 재사용해 주세요.

설정이 달라졌다면 결과를 섞어 비교하지 말고 차이를 명시해 주세요. 비교를 맞추기 위해 기존 프롬프트 문구를 바꿨다면, 변경 전 요청과 동일한 요청이라고 취급하지 않습니다.

API 호출은 가능한 한 필요한 추가 실험에만 사용해 비용과 할당량을 절약해 주세요.

#### 3-4. 평가 지표

각 조건에 대해 다음 항목을 비교합니다.

**수학 문제 풀이 성능**

- 정답 문항 수
- 정답률
- 세 조건 사이에서 정오답이 달라진 문항
- 최종 답은 맞았지만 풀이에 오류가 있는 사례

**토큰 사용량**

- 입력 토큰 수
- 출력 토큰 수
- 추론 토큰 수(확인 가능한 경우)
- 전체 토큰 수
- 문항당 평균 및 전체 합계

토큰 사용량의 세부 항목이 중복 집계되지 않도록 API 응답의 실제 필드 정의에 맞춰 처리해 주세요. API가 제공하지 않은 값은 `null` 또는 미제공으로 남기고 0으로 추정하지 않습니다.

**풀이 분석**

- 논리적 오류 유무
- 풀이 과정의 타당성
- 제공한 해설 빈도 벡터가 풀이에 도움을 준 것으로 보이는 사례
- 빈도 정보가 불필요하거나 오히려 혼란을 준 것으로 보이는 사례

풀이의 타당성은 최종 답의 정오답과 분리해서 평가해 주세요.

LLM을 이용한 풀이 검토가 포함된다면 자동 검토 결과를 확정적인 수학적 증명처럼 취급하지 말고, 판단 근거와 검토의 한계를 남겨 주세요. 실제로 검토하지 않은 항목은 미검토로 표시합니다.

#### 3-5. API 실행 및 기존 결과 재사용

현재 프로젝트의 `CompareGeneration.py`, `RateLimitedComparison.py`, `AnswerEvaluation.py` 등 기존 비교 코드를 먼저 확인하고 최대한 재사용해 주세요.

기존에 구현한 API 할당량 관리, 재시도, 중단 및 재개 기능을 유지합니다.

API 키는 환경변수나 기존 로컬 설정만 사용하며, 코드나 결과 파일에 노출하지 않습니다.

실행 전 예상 호출 수와 기존 재사용 가능 결과 수를 확인해 주세요.

API를 실제로 실행할 수 있는 환경이면 실험을 수행하고 결과를 저장하되, 키가 없거나 할당량이 부족하면 이미 완료된 결과까지 보존하고 미완료 항목을 명시해 주세요. 무제한 재시도는 하지 마세요.

### 4. 연구의 신뢰성 및 데이터 검증

이번 실험은 실제 결과를 해석하는 것이 목적이므로, 다음 조건을 반드시 검증해 주세요.

1. 기존 train/test 분할을 유지하고 학습·테스트 문항이 겹치지 않는지 확인합니다.
2. 어휘 목록은 기존처럼 학습 데이터에만 기반하여 생성되었는지 확인합니다.
3. 벡터의 각 행과 문항 ID가 정확히 대응하는지 확인합니다.
4. 군집화의 중심 및 회귀 모델의 가중치 학습에 테스트 데이터를 사용하지 않습니다.
5. 모델 성능 평가 전에 테스트 결과를 이용해 하이퍼파라미터를 유리하게 선택하지 않습니다.
6. 실제 해설 벡터는 회귀 평가와 오라클 조건 외에는 입력 정보로 유출되지 않도록 합니다.
7. API 조건마다 문제 텍스트, 프롬프트 설정, 벡터 처리 방식, 응답 및 토큰 사용량을 추적 가능하게 저장합니다.
8. 기존에 검토한 정답과 원본 정답이 불일치하는 문항이 있다면 그 사실을 기록하고 채점 기준을 구분합니다. AI 보조 검토와 사람의 확정 판정을 혼동하지 않습니다.

최종 보고서에서 평가 데이터의 규모와 반복 실험 횟수에 따른 한계를 반드시 설명해 주세요.

기존 테스트 결과를 이미 관찰한 뒤 후속 비교를 설계했다는 사실도 정직하게 기록해 주세요. 학습에 테스트 데이터를 넣지 않았다는 사실과, 테스트 결과를 전혀 본 적 없는 완전히 독립적인 최종 평가라는 주장을 구분합니다. 새로운 검증 실험을 무단으로 확대할 필요는 없습니다.

### 7. Gemini API 입력 과정의 완전한 검증

#### 7-1. 실제 Gemini에 전달되는 입력 확인

현재 프로젝트의 Gemini API 관련 코드 전체를 점검해 주세요.

특히 다음 파일과 연결된 함수들의 동작을 확인해 주세요.

- `GoogleAPI.py`
- `CompareGeneration.py`
- `RateLimitedComparison.py`
- 프롬프트 생성 및 빈도 벡터 직렬화 관련 코드

단순히 프롬프트를 생성하는 함수의 코드만 확인하는 것이 아니라, **최종적으로 Gemini API 요청에 들어가는 실제 내용을 확인하는 것**이 중요합니다.

각 조건에 대해 다음을 검증해 주세요.

1. 원본 수학 문제 텍스트가 누락되거나 변형되지 않았는가?
2. LaTeX 수식이 이스케이프 처리 과정에서 손상되지 않았는가?
3. 문제에 포함된 수식, 조건, 선택지가 모두 전달되는가?
4. 예측 빈도 벡터의 토큰과 수치가 정확하게 전달되는가?
5. 실제 해설 빈도 벡터가 의도한 형식으로 전달되는가?
6. 토큰의 이름과 빈도 값이 잘못 대응되지 않았는가?
7. 학습·테스트 문항의 ID가 뒤바뀌지 않았는가?
8. 문제만 제공하는 기본 조건에 빈도 벡터 정보가 들어가지 않는가?
9. 예측 조건에 실제 정답 해설 정보가 유출되지 않는가?
10. 세 조건 사이에서 비교 목적 외에 불필요한 프롬프트 차이가 발생하지 않는가?

API 호출 직전에 완성되는 요청 내용을 기준으로 확인해 주세요.

#### 7-2. 최종 프롬프트 저장

Gemini에 전달되는 실제 입력을 사람이 직접 검토할 수 있도록 저장해 주세요.

각 문항과 실험 조건마다 다음을 확인할 수 있어야 합니다.

- 문항 ID
- 실험 조건(A/B/C)
- 적용된 Gemini 모델 및 설정
- 시스템 지시문
- 사용자 메시지
- 수학 문제 원문
- 추가된 빈도 벡터 정보
- 최종 요청 메시지의 전체 텍스트
- 실제 호출에 사용한 요청 설정
- 입력 데이터의 출처
- 입력 해시 또는 재현 가능한 식별 정보

입력의 생성 코드만 보여주는 것이 아니라, **완성된 실제 프롬프트를 저장**해 주세요.

필요하다면 Gemini API에 요청을 보내기 직전의 내용을 기록하는 기능을 추가해도 좋습니다.

단, API 키와 인증 정보는 절대 로그에 기록하지 마세요.

#### 7-3. 실제 입력 예시 검토

대표적인 테스트 문항을 몇 개 선정해 다음 자료를 만들어 주세요.

**A 조건: 문제만 제공**

Gemini에 실제로 전달되는 전체 입력을 보여주세요.

**B 조건: 문제 + 예측 빈도 벡터**

A 조건과 비교했을 때 어떤 내용이 추가되는지 정확히 보여주세요.

**C 조건: 문제 + 실제 해설 빈도 벡터**

B 조건과 비교했을 때 빈도 벡터의 값과 토큰 구성이 어떻게 다른지 보여주세요.

특히 B와 C에서 빈도 벡터를 전달하는 형식은 동일해야 합니다.

각 조건의 차이가 눈에 잘 들어오도록 비교표와 입력 예시를 만들어 주세요.

#### 7-4. API 호출 전후 검증

실제 API 실행 전에 입력 생성 및 직렬화 과정에 대한 테스트를 수행해 주세요.

API 호출 이전에 최종 입력이 올바른지 확인하는 dry-run 기능이 있으면 좋겠습니다.

또한 실행 후에는 다음 항목을 확인해 주세요.

- 요청한 모델이 실제 사용되었는지
- 사용한 프롬프트와 저장된 프롬프트가 일치하는지
- API 응답이 해당 문항 ID와 정확히 연결되는지
- 응답 누락이나 중복 호출이 발생하지 않았는지
- 입력·출력·추론 토큰 사용량이 올바르게 저장되는지
- 오류가 난 문항을 정상적인 평가 결과로 잘못 집계하지 않았는지

요청 모델 식별자와 API가 제공하는 실제 모델 버전 정보를 구분해 기록합니다. 응답에서 확인할 수 없는 모델 내부 정보는 검증했다고 주장하지 마세요.

최종적으로 **Gemini에 어떤 데이터가 어떤 형식으로 전달되어 어떤 결과가 반환되었는지** 추적할 수 있어야 합니다.

### 9. 최종 실험 결과의 통합 및 시각화

#### 9-1. 결과물을 한곳에서 확인할 수 있도록 정리

현재 프로젝트에서 가장 불편한 점 중 하나는 실행 결과가 여러 파일과 폴더에 흩어져 있어, 실제로 어떤 결과가 나왔는지 확인하기 어렵다는 것입니다.

따라서 **최종 실험 결과를 하나의 폴더 아래 체계적으로 정리**해 주세요.

최종 결과 폴더의 최상위에는 `README.md` 또는 `index.html`을 제공하여 모든 자료를 쉽게 찾을 수 있도록 해 주세요.

위 구조는 예시이며, 기존 프로젝트 구조를 고려해 더 합리적인 형태로 수정해도 좋습니다. 같은 이름의 기존 결과가 있다면 덮어쓰지 말고 새 실험 식별자를 사용합니다.

다만 최종 결과물이 여러 경로에 중복 저장되거나, 임시 파일과 최종 파일이 뒤섞이지 않도록 해 주세요.

#### 9-2. 군집화 시각자료

다음 시각자료를 만들어 주세요.

**필수 시각자료**

- 분류 단계별 유클리드·코사인 기반 ARI 비교 그래프
- 분류 단계별 NMI 비교 그래프
- 실제 분류와 K-means 군집의 교차표 히트맵
- 군집별 실제 라벨 구성 비율 그래프

가능하다면 PCA를 사용한 2차원 군집 시각화도 포함해 주세요.

단, PCA 그래프는 고차원 데이터를 시각적으로 투영한 것이며, 실제 K-means가 2차원에서 학습한 것은 아니라는 점을 명시해야 합니다. PCA를 사용한다면 학습 데이터로만 맞추고, 어떤 표현 공간을 투영했는지 표시합니다.

세부 유형처럼 라벨이 많은 경우에는 하나의 거대한 그래프로 모든 정보를 표시하지 말고, 확대 가능한 이미지나 분할된 그래프를 사용해 주세요.

시각자료에서는 다음을 우선합니다.

- 한글 글꼴 정상 표시
- 명확한 축 이름과 범례
- 실제 수치를 확인할 수 있는 표시
- 적절한 이미지 해상도
- 일관된 색상과 디자인
- 보고서와 발표 자료에 활용 가능한 가독성

#### 9-3. 회귀 모델 시각자료

다음 자료를 만들어 주세요.

- 학습 과정의 손실함수 변화 그래프

특히 대표 문항에 대해서는 **실제 해설에서 중요한 토큰과 회귀 모델이 중요하다고 예측한 토큰이 어떻게 다른지** 한눈에 확인할 수 있도록 해 주세요.

여기서 빈도가 높다는 사실과 수학적으로 중요한 개념이라는 판단은 구분합니다. 그래프는 우선 ‘빈도가 높은 토큰’을 보여주고, 수학적 중요성에 관한 해석은 별도로 표시해 주세요.

#### 9-4. Gemini API 시각자료

다음 자료를 만들어 주세요.

- A·B·C 조건의 정답률 비교

- 출력 토큰 사용량 비교
- 추론 토큰 사용량 비교(가능한 경우)
- 전체 토큰 사용량 비교
- 문항별 조건에 따른 정오답 변화
- 문항별 토큰 사용량 차이

특히 문항별 비교표에서 다음 정보가 한 행에 표시되도록 해 주세요.

| 문항 ID | 실제 정답 | A 답 | B 답 | C 답 | A 정오 | B 정오 | C 정오 | A 토큰 | B 토큰 | C 토큰 |
|---|---|---|---|---|---|---|---|---|---|---|

필요한 세부 정보는 추가 열이나 별도 상세 자료로 제공해도 좋습니다. 정답표 충돌, 채점 불가, API 미완료 항목도 구분해 표시합니다.

각 조건의 정답률만 보여주는 것이 아니라, **어떤 문제에서 성능이 개선되거나 악화되었는지 직접 확인하는 것**이 목적입니다.

#### 9-5. 사람이 직접 분석할 수 있는 자료

자동 생성된 결론만 읽고 끝내고 싶지 않습니다.

연구자인 제가 직접 결과를 보고 분석할 수 있도록, 원본 결과와 해석용 자료를 함께 제공해 주세요.

특히 다음 사례를 쉽게 찾을 수 있도록 정리해 주세요.

- 실제 유형과 군집이 잘 일치한 문제들
- 서로 다른 유형인데 같은 군집으로 묶인 문제들
- 동일한 유형인데 다른 군집으로 나뉜 문제들
- 회귀 모델이 해설 토큰을 잘 예측한 문제들
- 회귀 모델의 예측이 크게 벗어난 문제들
- 예측 벡터가 Gemini에 도움이 된 것으로 보이는 사례
- 실제 해설 벡터에서도 개선되지 않은 사례
- A·B·C 조건 간 정답이 서로 다른 사례

각 사례에 대해 원본 문제, 실제 분류, 관련 벡터, 모델 결과를 직접 확인할 수 있도록 해 주세요.

**가능하면 문항 ID를 중심으로 모든 결과를 연결해 주세요.**

예를 들어 하나의 문제를 선택하면 군집 배정, 회귀 예측, Gemini 입력과 응답까지 찾아볼 수 있는 구조가 이상적입니다.

별도의 복잡한 웹 애플리케이션 개발은 필요하지 않습니다. CSV, Markdown, 정적 HTML 등 간단한 방법으로 충분합니다.

## 1. 수학 문제와 풀이를 실제로 읽기 편하게 만들기

### 1-1. 문항별 비교 화면의 수식·Markdown 표시

최종 결과의 문항별 비교 HTML과 그 생성 코드를 확인하세요. LaTeX와 Markdown을 단순히 `<pre>`에 출력하는 부분이 있다면, 읽기용 화면에서는 정상적으로 표시되도록 수정하세요.

- LaTeX 분수, 극한, 지수·첨자, 절댓값, 경우 나누기 등을 수학식으로 렌더링합니다.
- Markdown 제목, 문단, 목록, 강조, 표도 읽기 좋게 표시합니다.
- A 문제만 / B 예측 해설 토큰 / C 실제 해설 토큰의 구분을 유지합니다.
- 문제 원문과 선택지를 보기 쉽게 보여 주고, 원본 정답·해설은 펼쳐서 확인할 수 있게 합니다.
- 문항 ID로 검색할 수 있고, 조건 간 정오답이 달라진 문항을 쉽게 찾을 수 있게 합니다.
- 화면이 좁으면 세 열을 억지로 유지하지 않고 세로로 배치합니다. 긴 수식과 표는 잘리거나 겹치지 않게 합니다.
- API 미실행·실패·채점 불가·검토 보류는 각각 구분하고, 이를 오답이나 0토큰으로 표시하지 않습니다.

**보기 좋은 표시와 원본 기록은 분리하세요.** 감사용 실제 입력, 시스템 지시, 응답 원문, 사용량, 해시는 그대로 보존하고, 화면에 별도의 접이식 ‘원문 보기’를 제공하세요. 수식 렌더링을 위해 API 입력이나 응답 파일 자체를 치환·수정하면 안 됩니다.

Markdown·LaTeX·HTML 처리 순서를 검토하여 백슬래시 손상, 이중 이스케이프, 코드 블록 오인식이 없게 하세요. 모델 응답에 포함된 임의의 HTML이나 스크립트가 실행되지 않도록 안전하게 처리하세요. 렌더링에 실패한 부분은 원문으로 남기고 실패 사실을 표시하며, 식을 추측해서 고치지 마세요.

### 1-2. 군집별 문제도 읽을 수 있게 연결

군집 목록에는 문항 ID, 학습/테스트 구분, 실제 과목·단원·세부단원·유형을 유지하세요. 원본 문제를 확인하기 위해 여러 폴더를 뒤져야 하지 않도록, 해당 문항의 읽기용 화면 또는 명확한 원문 링크로 연결하세요.

가능하면 기존 정적 뷰어를 재사용해 군집에 속한 문제의 수식을 읽을 수 있게 하세요. 학습 문항처럼 Gemini 비교 대상이 아닌 문제는 ‘생성 실험 대상 아님’으로 표시하며, 누락 응답으로 오인하거나 추가 API 호출을 하지 마세요.

새 웹 서비스, 서버, 로그인 기능, 대형 프런트엔드 프로젝트는 만들지 마세요. 기존 보고서 생성 기능과 정적 HTML·Markdown을 우선 활용하세요. 수식 표시 때문에 비공개 문제나 응답을 외부 렌더링 서버 또는 공개 사이트에 업로드하지 마세요.

외부 스크립트가 필요한 경우 의존성과 인터넷 연결 필요 여부를 명시하고, 가능하면 로컬에서도 읽을 수 있도록 구성하세요. 구현 라이브러리 선택보다 실제 출력의 가독성이 우선입니다.

## 2. 내가 볼 결과 파일의 시작점을 명확하게 만들기

`results/final_experiment/README.md` 또는 실제 사용하는 최종 결과 안내를 중심으로, 다음 자료에 바로 접근할 수 있게 정리하세요.

| 확인할 내용 | 안내에서 바로 연결할 자료 |
|---|---|
| 전체 실험 결과 | 최종 보고서와 핵심 수치·그림 |
| 군집별 실제 문제 | 4개 분류 수준 × 2개 방식의 군집 목록과 비교표 |
| 회귀 예측 | 문항별 실제·예측 토큰 비교와 벡터 오차 |
| Gemini 세 조건 | 수식이 표시되는 문항별 비교 HTML |
| 실제 모델 입력 | 완성된 요청·전송 토큰·응답 원문 |
| 문제 하나의 전체 결과 | 문항 ID를 중심으로 연결된 결과 |

**사용자가 처음 열 파일, 다음에 볼 파일, 자세한 근거 파일을 구분하세요.** README·CSV·JSON을 많이 만드는 것 자체가 목표가 아닙니다. 요약에서 관심 있는 문항과 원자료까지 쉽게 따라갈 수 있어야 합니다.

표·그림은 저장된 결과에서 생성하고, 제목·축·범례·평가 대상·학습/테스트 구분을 명확히 표시하세요. 큰 유형별 히트맵은 글자가 읽히도록 나누고 전체 표로도 연결하세요. 기존 그림이 충분하면 새 그림을 중복 생성하지 마세요.

최종 안내에 비교 HTML의 경로와 여는 방법을 적으세요. 저장소의 파일 페이지와 브라우저에서 실행하는 HTML 화면을 구분하고, 파일 하나만 내려받아도 되는지 관련 폴더가 필요한지도 명시하세요.

상대 경로와 링크를 실제 파일 위치에 대조하세요. 특히 하위 폴더의 `clusters.md`, 문항별 연결 문서, 그림 링크, 삭제된 파일을 가리키는 링크를 확인하세요. 특정 작업 환경의 `/workspace/...` 경로를 사용자가 그대로 써야 하는 실행 경로처럼 안내하지 마세요.

## 3. RunTraining 삭제 이후에도 새 실험을 이어갈 수 있게 만들기

### 3-1. 파일명 복구보다 기능의 연결을 확인

`RunTraining.py`라는 이름의 파일을 반드시 복구할 필요는 없습니다. 현재 대체된 실행 경로가 같은 역할을 수행한다면 유지하세요.

다만 ‘과거 결과를 다시 읽는 기능’과 ‘새 모델을 학습하고 평가하는 기능’을 명확히 구분해야 합니다. `FinalClustering.py`, `TorchRegression.py`, `VectorComparison.py`, `ThreeWayGeneration.py`, 보고서 생성 코드 등의 현재 연결을 확인하세요. 파일명이 바뀌었다면 실제 저장소를 기준으로 판단하세요.

특히 회귀 모델을 새로 학습해도 벡터 비교 프로그램이 과거 폴더의 고정 모델을 계속 불러오는 구조라면, 사용자가 의도한 모델과 다른 모델을 평가하지 않도록 수정하세요.

### 3-2. 같은 실험의 데이터·모델·결과를 끝까지 연결

다음 흐름이 명시적인 설정으로 연결되어야 합니다.

선택한 데이터와 학습 어휘 → 학습 또는 지정 체크포인트 로딩 → 해당 모델의 예측 → 해당 예측의 평가 → 선택적으로 Gemini 입력 준비 → 저장된 결과의 보고서 생성

실험별로 최소한 다음을 지정하거나 확인할 수 있어야 합니다.

- 실험 이름과 결과 저장 경로
- 사용할 문제·해설 벡터 및 어휘 목록
- 사용할 고정 학습·테스트 ID
- 새로 학습할지, 검증된 기존 모델을 사용할지
- 사용할 체크포인트와 예측 파일
- 후속 비교·보고서가 읽을 결과 경로

설정 방식은 기존 구조에 맞게 단순하게 선택하세요. 복잡한 범용 실험 프레임워크나 새로운 설정 파일 여러 개를 만들 필요는 없습니다. 같은 값을 여러 파일에서 각각 수정해야 한다면 가능한 범위에서 한곳으로 모으세요.

기존 회귀 결과 재사용 경로는 보존하되, 특정 과거 결과 폴더가 모든 새 실험의 유일한 입력이 되도록 하드코딩하지 마세요. 필요한 기존 모델은 기본값으로 지정할 수 있지만, 실제 선택된 모델·데이터·출력 경로를 실행 시와 결과에 명확히 남기세요.

중복 코드를 만들지 않고도 가능하다면 새 실험의 학습·평가를 적은 수의 명령으로 실행할 수 있게 하세요. 통합 실행기가 필요하면 기존 함수를 호출하는 얇은 연결 파일 정도로 제한하세요.

### 3-3. 다른 실험 결과가 조용히 섞이지 않도록 검증

불용어 제거 등으로 어휘가 바뀌었는데 과거 모델을 그대로 사용하는 상황을 막아야 합니다. 입력·출력 차원뿐 아니라 어휘의 내용과 순서, 문항 ID와 행 순서, 학습/테스트 분할, 데이터 식별 정보, 모델 및 예측 파일의 대응 관계를 검사하세요.

같은 차원이라도 어휘 순서가 다르면 다른 데이터입니다. 호환되지 않는 경우 경고만 남기고 계속하지 말고, 어떤 파일이 불일치하는지 설명하며 중단하세요. 필요한 모델이나 예측이 없을 때 과거 결과를 자동으로 대신 가져오지도 마세요.

원시 빈도는 정수, 회귀 예측은 실수로 보존합니다. 기존 음수 보정과 전송 시 소수점 표시 규칙은 임의로 바꾸지 마세요.

## 4. 결과 열람과 재실험을 안전하게 분리하기

실행 방법을 다음처럼 구분해 README에 적으세요.

| 작업 | 허용되는 동작 |
|---|---|
| 기존 결과 읽기·화면 다시 만들기 | 저장된 데이터만 읽음. 재학습·API 호출 없음 |
| 기존 모델 다시 평가하기 | 지정한 체크포인트로 예측·평가. 재학습·API 호출 없음 |
| 새 모델 학습하기 | 사용자가 지정한 별도 실험 경로에 학습·예측·평가 결과 저장 |
| Gemini 입력 준비·검증 | 실제 요청 내용을 생성하고 확인. API 호출 없음 |
| Gemini 실제 호출 | 사용자가 명시적으로 선택한 경우에만 실행 |

이번 보완 작업에서는 기존 실험과 API 응답을 재사용하고, 보고서의 표시만 바뀌었다는 이유로 Gemini를 다시 호출하지 마세요. 새 학습 경로는 작은 가짜 데이터나 임시 폴더의 검사로 검증할 수 있습니다. 검사 데이터를 실제 연구 결과에 섞지 마세요.

표시용 코드 변경과 모델·입력·프롬프트의 의미 변경을 구분하세요. 화면을 개선했다는 이유만으로 완료된 실험을 다른 실험으로 취급하거나 기존 감사 기록을 다시 쓰면 안 됩니다. 반대로 입력이나 모델이 실제로 바뀌었을 때 이전 캐시를 재사용해서도 안 됩니다.

## 5. 저장소는 정리하되, 필요한 근거는 보존하기

현재 최종 실행에 쓰이지 않는 중복 진입점、폐기된 표시 코드、임시 산출물은 참조 여부를 확인한 후 정리하세요. 다만 파일 개수를 줄이려고 핵심 검증이나 서로 다른 역할의 모듈을 없애거나 거대한 파일 하나로 합치지 마세요.

과거 결과 폴더에는 현재 재사용하는 모델·API 응답·정답표 충돌 근거가 있을 수 있습니다. **이 폴더를 통째로 삭제하지 마세요.** 현재 코드에서 필요한 자료를 정확히 확인하고, 최종 안내에서는 ‘현재 분석할 결과’와 ‘재현성·출처 확인용 보존 자료’를 분리해 표시하세요.

후속 실험을 막을 정도로 학습 기능을 없애지 마세요. 원본 HML·문제·해설·출처、학습/테스트 분할、학습 어휘、모델、원본 요청·응답、사용량과 핵심 감사 기록을 보존하세요. 최소한의 핵심 테스트도 유지하세요.

정리 전 복구 가능한 Git 체크포인트를 남기고, 미추적 파일은 Git 이력만으로 복구된다고 가정하지 마세요. 사용자 변경을 보호하고, 비밀값·API 키·`.env`는 커밋하거나 보고서에 노출하지 마세요. 새 백업·새 안내·새 로그를 불필요하게 여러 벌 만들지 마세요.

## 6. 완료 전에 실제로 확인할 사항

1. 최종 결과 안내에서 군집 목록·회귀 비교·Gemini 비교 화면·원문에 접근할 수 있는가?
2. 실제 저장된 대표 문항의 분수·극한·첨자·경우 나누기와 Markdown이 읽기 좋게 표시되는가?
3. 좁은 화면과 긴 수식에서도 내용이 겹치거나 잘리지 않는가?
4. 상대 링크가 유효하고, 삭제된 파일 또는 특정 환경 경로를 잘못 가리키지 않는가?
5. 표시 수정 전후의 원본 문제·요청·응답·모델·핵심 결과 수치가 보존되는가?
6. 결과 열람·보고서 재생성 과정에서 학습 함수나 실제 API 호출이 실행되지 않는가?
7. 새 실험 경로를 선택하면 평가·비교·보고서가 그 경로의 데이터와 모델을 사용하고, 과거 결과로 조용히 돌아가지 않는가?
8. 차원이 같아도 어휘 순서가 다른 모델·데이터 조합을 거부하는가?

파일이 존재한다는 검사만으로 가독성 검증을 대신하지 마세요. 가능한 환경에서는 HTML을 실제로 열어 확인하세요. 브라우저나 렌더링 검사를 할 수 없었다면 확인한 범위와 확인하지 못한 부분을 구분해서 보고하세요.
