# 신규3회 반복 연구 보고서

## 목적과 실제 실행 범위

출력 토큰 대조군 5문항과 기존 오답 관련 11문항을 합쳐 13개 고유 문항의 186요청을 계획했다. 현재 신규 API 응답 수신 186/186(정상 완료 183, 불완전 3), 미수신 0이다. 이전 265문항의 응답은 비교 기준으로만 읽고 신규 3회로 세지 않았다.

실행 기록상 SDK 생성 시도는 **238회**(통신실패 재시도 포함), 모델 메타데이터 조회는 4회다. 이는 고유 반복 관측 186개와 구분한다. 응답을 이미 받은 반복을 추가로 생성하지 않았으며, 전송 실패 재시도도 실행 이력에서 삭제하지 않았다.

A는 기존 문제만, B/C는 동결된 Ridge/MLP 예측 힌트, D는 실제 해설 토큰, E는 문제 뒤 ‘풀이를 작성해줘.’만 추가한 조건이다. F는 D의 동일한 토큰·빈도·JSON에서 출처 제목만 ‘해설에 등장한 토큰과 빈도: 상위20개’로 바꾼 조건이다. 가짜 토큰·새 예측·새 학습은 없다.

**반복 간 관찰:** 3회를 모두 수신한 62개 문항·조건 중 62개에서 세 응답 본문이 바이트까지 같았고, 62개에서 출력 토큰의 표본 SD가0이었다. 응답을 복사한 것이 아니라 반복마다 신규 호출했다. temperature0에서 관측한 반복 안정성이며, 서로 독립인 세 무작위 표본의 성공이나 오류 확률 추정으로 해석하지 않는다.

같은 5문항을 조건당3회 반복한 설명 통계다. 출력이 짧아진 쌍만 사후 선택한 이 표로 토큰 감소가 정답이나 수학적 타당성을 바꾼 인과효과를 추정하지 않는다.


**출력 제한·불완전 응답도 연구 결과에 포함했다.**

큰 사용량을 가진 응답은 평균·SD를 크게 바꿀 수 있다. 이를 제외하거나 같은 반복을 다시 생성하지 않았으며 문항별 그림의 개별 반복 점과 최소~최대에서 직접 확인할 수 있다.

이 대응 횟수는 같은 11문제를 반복 관측한 설명 통계다. 풀이가 달라져도 수학적으로 타당할 수 있고, 동일 오류를 놓치지 않았는지는 아래 실제 식·계산·반례를 포함한 AI 보조 검토에서 확인해야 한다.

기존의 틀린 최종 답과 논리 오류가 새 응답에서도 나타나는지는 새 풀이의 잘못된 식·올바른 계산·반례와 함께 [A-D 상세](error_repeat_11/AD_detailed_analysis.md), [B-C 상세](error_repeat_11/BC_detailed_analysis.md)에 기록했다. 정답 횟수가 같더라도 풀이 타당성이 같다고 볼 수 없다. 중간 오류를 스스로 수정한 경우와 최종 답은 맞지만 오류를 남긴 경우를 구분했다.

## 판단의 근거와 불확실성

3회 표본 SD는 **ddof=1**이다. 사용량이 제공된 API 수신 응답이0개면 평균·최소·최대·SD는 —, 1개면 SD는 —다. 미제공은 null/—이며0으로 채우지 않는다.
**출력 제한(MAX_TOKENS)·차단·빈 응답도 API 응답을 받은 한 번의 반복이다. 같은 반복을 다시 뽑지 않는다.** 잘린 응답의 실제 토큰은 사용량 평균에 포함하지만, 최종 답이 완성되지 않았다면 채점 보류로 남긴다. 설정된 토큰 상한을 실제 사용량 대신 넣지 않는다.
정답 횟수와 풀이 타당 가능 횟수는 별개다. 검토 보류를 오류로 간주하지 않으며 AI 보조 검토는 사람의 확정이나 형식적 증명이 아니다. 자기 수정 횟수는 일부 중간 오류의 명시적 수정을 뜻하며, 다른 오류가 남아 최종 오답·풀이 부적절과 함께 나타날 수도 있다. 기존 오류 재발은 해당 잘못된 단계가 새 풀이에 다시 등장했는지를 뜻하므로, 이후 고친 경우에도 예로 기록될 수 있다. 최종 논증의 타당성과 자기 수정 여부를 함께 읽는다.
같은 문항·같은 반복 번호를 대응시켰지만 조건 순서가 섞인 탐색적 비교다. 3회 모두 정답이어도 오류 가능성이 사라졌다고 주장하지 않는다.
11문항은 과거 오답을 보고 선정했으므로 선택 편향이 있다. 전체 265문항 또는 기존 테스트 80문항의 정답률과 동등한 성능 평가가 아니다. B/C는 전체 265문항의 어휘를 미리 아는 조건이며 학습 185문항에 대한 예측은 인샘플이다.
표본 3회와 이번 실행 자료만으로 차이의 원인을 모델 능력·지시문·힌트·출처 강조 중 하나로 확정할 수 없다. 3회 모두 정답이어도 해당 오류가 영원히 재현되지 않는다는 뜻이 아니다. API 입출력 토큰과 외부 모델의 전체 연산 비용은 별개이며, 측정하지 않은 전체 시스템 효율 향상은 주장하지 않는다.

## 보존과 재현

[설정](config.json), [실제 프롬프트](frozen_prompts/), [신규 응답](responses.jsonl), [실행 상태](state.json), [검증](validation.json)을 보존한다. 모든 핵심 수치는 저장된 새 응답에서 생성했으며 report/verify는 학습·API를 실행하지 않는다.

동결된 config.json의 cache_policy에는 관측 전의 ‘success’ 표현이 해시 보존을 위해 남아 있다. 첫 잘림 응답을 관측한 뒤 반복 슬롯을 다시 뽑는 선택 편향을 막도록 **실제 API 응답을 받은 슬롯은 정상 종료 여부와 관계없이 한 번의 관측으로 종료**하는 정책을 명시했다. 현재 완료 수와 미수신 목록은 state.json의 completed_requests/api_response_count를 기준으로 읽는다. 모델·프롬프트·출력 상한·토큰은 바꾸지 않았다.

통신 정책 변경: 117개 응답을 보존한 뒤 HTTP/서버 응답 대기 상한을 180초에서 300초로 늘렸다. 실제 HTTP504 및 읽기 타임아웃에 따른 전달 대기 변경이며, SDK의 X-Server-Timeout에도 반영된다. 문제·힌트·모델·temperature·thinking·최대 출력8192는 그대로이고 이미 받은 정상·출력 제한 관측을 다시 뽑지 않았다. 요청별 대기 상한은 SDK 캡처·응답·실행 이력에 따로 남긴다. 이 실행 시점/통신 정책 차이도 작은 반복 실험의 한계로 고려한다.

이번 산출물은 3회 반복 결과의 정리까지이며 프로젝트 전체의 최종 결론을 확정하거나 후속 실험을 자동 실행하지 않는다.
